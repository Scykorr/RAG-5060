Ранее для этой локальной ветки RAG был спроектирован следующий стек; **не воспринимай его как подтверждение состояния развёрнутого кода**:

| Компонент | Ранее согласованный ориентир | Действие Cursor |
|---|---|---|
| Хост | Windows 11; 32 ГБ RAM; RTX 5060 Ti 16 ГБ VRAM | Проверить фактические ресурсы |
| Диски | системный SSD — небольшой свободный остаток ~20–30 ГБ; HDD для данных около 2 ТБ | Проверить пути/остатки; не размещать тяжёлые кеши на системном SSD |
| Среда | Linux-контейнеры через Docker Engine в WSL2, без обязательного Docker Desktop | Использовать уже работающий способ развёртывания |
| Frontend | React + TypeScript + Vite, единый web UI | Проверить код; встроить новый маршрут в существующую навигацию |
| Backend | Python / FastAPI / Pydantic / SQLAlchemy / Alembic | Проверить текущие версии и организацию слоёв |
| Метаданные | PostgreSQL | Использовать существующий кластер/миграции, без второй обязательной БД |
| Очереди | Celery + Valkey, возможны отличия в текущем коде | Подключить новую очередь/маршрутизацию без поломки существующих заданий |
| Векторы | Qdrant | Через существующий слой доступа к векторному поиску и его ACL |
| LLM | Ollama, ориентир `qwen3:8b` локально | Только опционально, с ограничением ресурсов и валидацией вывода |
| Embeddings | BAAI/bge-m3 CPU-сервис; модель/версии могут измениться | Повторно использовать готовые векторы и модель, не вычислять всё заново |
| Извлечение | Docling / собственный ingestion; chunk/page/section | Использовать достоверные извлечённые тексты и координаты источников |
| Контур знаний | предложено → проверено → утверждено/отклонено, аудит | Сохранить/переиспользовать эти статусы, не публиковать LLM-гипотезы как знания |

**Профиль приёмки первого релиза:** 100–500 документов, один тяжёлый ingestion/LLM job и один ответ модели одновременно — это стартовая точка, не жёсткий лимит архитектуры. Возможность работы на 100 000+ документах — цель масштабирования, **не обещание производительности на текущем ПК**.

# 1. ЦЕЛЬ, РАМКИ И УСЛОВИЯ ПРИЁМКИ

Создать **Graph Explorer**: красивый, быстрый, интерактивный и расширяемый веб-граф связности документальной базы RAG, сравнимый по удобству с графом Obsidian, но с более строгой доказательной моделью.

Пользователь должен видеть:

- **глобальный граф** по доступным коллекциям и документам (с группировкой по темам, папкам, типам, источникам; без массовой передачи всего корпуса в браузер);
- **локальный граф** выбранного документа на 1, 2 или 3 перехода (сверять права на каждой вершине/ребре);
- **прямые ссылки** «ссылается на» и «упоминает», **семантическое сходство** по embeddings, общие сущности/темы, отношения версий, позднее — «дополняет» и «потенциально противоречит»;
- различие **фактически подтверждённой**, **автоматически вычисленной** и **предположенной LLM** связи;
- при нажатии на ребро — **почему оно возникло**: тип, источник, пара документов/версий, фрагменты текста, page/section/chunk, оценки/метод извлечения, кем и когда подтверждено;
- при нажатии на узел — карточку документа, метаданные, доступные версии, переход в существующий просмотрщик, список соседей и связанных документов;
- поиск, фильтры, легенду, масштабирование, выделение, миникарту (если это оправдано), тёмную/светлую тему в стилистике текущего UI;
- очередь анализа, ход построения графа, ошибки и повторы для административного/экспертного интерфейса;
- возможность экспертного принятия/отклонения/редактирования связей с аудитом.

**Важное разграничение:** граф связанности документов ≠ граф фактов и знаний. В MVP главный уровень — **документы и их версии**. Сущности/темы — необязательный дополнительный слой. LLM-выводы не становятся истинными автоматически. Позднее можно построить GraphRAG поверх утверждённых отношений, не ломая базовую модель.

## 1.1. Что НЕ делать в MVP

- Не делать Obsidian обязательным интерфейсом, не переносить корпус в Markdown vault и не синхронизировать файлы ради визуализации.
- Не создавать новую LLM или обучать/дообучать модель для графа.
- Не подменять существующий векторный поиск графовым; начальная интеграция — **чтение и визуализация**, а не изменение цепочки генерации ответов.
- Не применять LLM к каждому сочетанию документов: сложность `O(N²)` недопустима.
- Не внедрять отдельный кластер Neo4j/Elasticsearch/Kafka только ради графа.
- Не считать похожие документы фактологически согласованными.
- Не пытаться отображать миллион узлов в одном Canvas; использовать серверную выборку, кластеризацию, разворачивание по запросу.

## 1.2. Приоритеты

**P0 — обязательно:** аудит репозитория, БД/миграции, API, ACL, подтверждённые метаданные, семантические связи по существующим vectors (если доступны), локальный/глобальный граф, карточки, фильтры, обработка обновления/удаления/версий, тесты, offline сборка, документация.  
**P1 — в той же поставке, если платформа поддерживает:** извлечение явных ссылок, объяснение ребра на уровне цитируемых чанков, управление кандидатами экспертом, прогресс задач, JSON/CSV экспорт с ACL, удобные layouts.  
**P2 — отдельный отключаемый этап:** извлечение сущностей и отношений LLM, обнаружение потенциальных противоречий, группировки по темам, интеллектуальный поиск путей, использование утверждённого графа в retrieval, advanced analytics.

**Не подключать** библиотеку с непроверенной non-commercial, source-available-only, платной enterprise-only или запрещающей модификацию лицензией. **Запрещённая зависимость:** скачивание JS, шрифтов, изображений, аналитики или моделей с внешних ресурсов при открытии локального сайта. Документационные URL могут остаться в README, но работа приложения не должна обращаться к ним.

## 3.1. Правила интеграции

Предпочтительная логическая архитектура:

```text
existing RAG web app (React/TS or actual UI)
  ├─ existing navigation / documents / search / auth
  └─ /graph  — Graph Explorer (new page, same session/auth/theme)
         ├─ local/global modes, filters, search, evidence drawer
         └─ GET/POST /api/graph/...  (existing backend/API prefix)
                      │
             Graph API + ACL-aware query service
               ├─ GraphRepository / graph migrations (existing SQL DB)
               ├─ DocumentAdapter (existing documents, versions, chunks)
               ├─ VectorNeighborAdapter (existing vector store / Qdrant)
               ├─ GraphBuildService (candidate edges, provenance, rule engine)
               ├─ LocalRelationAnalyzer (optional LLM, default OFF)
               └─ GraphJobs (existing queue, low priority)
                      │
            postgres graph_* / audit_* / outbox (where appropriate)
```

Размещай файлы **в соответствии с реальной организацией репозитория**. Нижеописанные имена (`graph_*`, `/api/graph`) — желаемые контракты, но не повод ломать действующие API; точную структуру документировать. Не дублировать ORM-модели документов, ACL, user session, API client, ошибки и навигацию.

# 4. ДОМЕННАЯ МОДЕЛЬ: УЗЛЫ, РЁБРА, ДОКАЗАТЕЛЬСТВА

## 4.1. Узлы (GraphNode)

MVP узлы: `DOCUMENT` (документ как логический объект), `DOCUMENT_VERSION` (если пользователь включил версии). Опционально отдельные `TOPIC`, `ENTITY`, `COLLECTION` — **только при наличии реально подтверждённой модели**, без вымышленных сущностей.

Поля ответа API для узла (схематично):

```json
{
  "id": "doc:<opaque-id>",
  "type": "DOCUMENT",
  "document_id": "<opaque-id>",
  "active_version_id": "<opaque-id>",
  "label": "Краткое безопасно экранируемое название",
  "status": "PUBLISHED",
  "collection": "Технические документы",
  "mime_type": "application/pdf",
  "accessible": true,
  "relation_count_visible": 8,
  "size_class": "medium"
}
```

- ID в браузере — стабильный идентификатор, не физический путь/filename, не UUID, собранный без проверок.
- API **не должен** возвращать полный текст, приватные токены, исходные абсолютные пути, недоступные метаданные или секреты.
- Для `DOCUMENT` свяжи граф только с **опубликованной активной версией**, если пользователь не выбрал специальный режим просмотра истории.
- Неподдержанные/битые документы должны иметь понятное состояние `NOT_INDEXED`/`NO_EMBEDDINGS` (согласуй с фактическими статусами), а не пропадать без объяснения.

## 4.2. Типы рёбер (GraphEdge)

| Внутренний тип | Визуальная подпись | Ориентация | Кто вправе создавать | Доказательность |
|---|---|---|---|---|
| `SEMANTIC_SIMILAR` | Похож по смыслу | неориентированное | алгоритм embeddings | только мера сходства, не факт |
| `EXPLICIT_REFERENCE` | Ссылается на | A → B | детерминированный парсер/эксперт | текстовое упоминание с доказательством |
| `SHARES_ENTITY` | Общая сущность | неориентированное | валидатор/эксперт | перечисленные сущности и доказательства |
| `SAME_FAMILY` | Версия/семейство | зависит от связи | система версий/эксперт | документальные метаданные |
| `SUPERSEDES` | Заменяет | A → B | версия/эксперт | только при надёжном основании |
| `EXTENDS` | Дополняет | A → B | LLM-кандидат/эксперт | гипотеза до подтверждения |
| `POTENTIAL_CONTRADICTION` | Возможное противоречие | неориентированное | LLM-кандидат/эксперт | не объявлять установленным противоречием |
| `MANUAL_LINK` | Связь эксперта | направленное или нет | уполномоченный пользователь | причина и журнал автора |

Внешне могут быть **несколько разных рёбер между одной парой документов**, но нельзя плодить точные дубликаты одного и того же утверждения. Для симметричных типов нормализовать порядок пары по стабильно сравниваемым идентификаторам; для направленных сохранить направление. Между двумя документами может быть несколько независимых evidence с одним ребром. Связи по версиям должны явно хранить версии обоих концов.

## 4.3. Достоверность, оценка и жизненный цикл

**Разделять три независимые оси:**

1. `origin`: `SYSTEM_RULE` / `VECTOR` / `LOCAL_LLM` / `HUMAN`;
2. `review_state`: `PROPOSED` → `PENDING_REVIEW` → `APPROVED` / `REJECTED`; при устаревании — `STALE` / `RETRACTED` / `SUPERSEDED`;
3. `confidence_score`: числовая величина **только если её метод вычисления известен**; для человеческих/фактических ссылок допускается `null`. Не смешивать cosine с вероятностью истинности.

- `APPROVED` не означает, что утверждение навсегда истинно: при смене источника связь становится `STALE`, требует ревалидации.
- У каждой связи хранить `algorithm_name`, `algorithm_version`, `embedding_model_id`, `prompt_template_hash` (для LLM), время построения, `run_id`, `source_revision`/`document_version`, авторов/ревьюеров.
- Система не должна выдавать тип `EXPLICIT_REFERENCE`, если документ просто тематически похож.
- По умолчанию показывать пользователю подтверждённые и вычисленные связи **с заметным обозначением метода**; неподтверждённые содержательные гипотезы LLM доступны в режиме эксперта или отдельном явно помеченном режиме, не выдаются за факты.
- **Запрещено** автоматически публиковать знания в основной RAG-корпус по результатам LLM. Утверждение связи в графе и утверждение нового знания в RAG — разные процессы; при связывании использовать существующие governance-состояния.

## 4.4. Доказательства (GraphEvidence)

Для каждого ребра поддержать одно или несколько доказательств с полями:

- `edge_id`, `source_document_version_id`, `source_chunk_id`, `target_document_version_id`, `target_chunk_id` (там, где применимо);
- исходная страница (`page`), заголовок/`section_path`, границы span/offset или структурный якорь Docling, если они надёжно известны;
- короткий, проверяемый фрагмент с обеих сторон **только по отдельному авторизованному запросу**, не в общем графовом JSON;
- `method`, `score_raw`, `score_normalized` при наличии обоснованной методики, `model_version`, timestamps;
- `explanation` как недоверенный текст, в UI строго экранированный;
- provenance: SHA256/идентификатор опубликованной версии, `run_id`, метаданные ревью;
- статус доказательства: `VALID`/`STALE`/`MISSING` без фальсификации, если страница/чанк больше недоступны.

Если совпадение вычислялось на чанках, нужен хотя бы один конкретный исходный chunk-pair, не «LLM считает похожими». Если сравнение было лишь на агрегированных документах — явно показывать метод и **не выдумывать подтверждающий отрывок**. В документе могут быть совпадающие заголовки и boilerplate; подавлять их вес.

## 4.5. Предлагаемая схема SQL (адаптировать по итогам аудита)

**Не создавай дубликаты таблиц документов и пользователей**. Новые таблицы называй в стиле проекта, логически требуются:

- `graph_edges`: `id`, `tenant_id`, `source_document_id`, `target_document_id`, `source_version_id`, `target_version_id`, `relation_type`, `directed`, `origin`, `review_state`, `score`, `score_method`, `created_at`, `updated_at`, `created_by`, `reviewed_by`, `reviewed_at`, `algorithm_version`, `model_id`, `run_id`, `stale_reason`, `deleted_at`, `payload_version`;
- `graph_evidence`: `id`, `edge_id`, source/target chunk IDs и version IDs, page/section/span или якоря, method/raw_score, content hash, status, created_at (при необходимости хранить текст только в основном защищённом хранилище, а не дублировать);
- `graph_build_jobs` либо расширение существующей таблицы jobs: `id`, `tenant_id`, `document_id`, `source_version_id`, `mode`, `state`, `progress`, `attempts`, `error_code`, `request_id`, lease/heartbeat, `created_at`/`finished_at`, `worker_version`;
- `graph_review_events` либо использование существующего append-only аудита: `actor`, `action`, `old_state`, `new_state`, `reason`, `timestamp`, `trace_id`;
- `graph_settings` при необходимости и только в scope tenant/user: включённые типы рёбер, пороги и лимиты;
- `graph_build_cursor`/high-watermark для пакетной обработки и дозавершения после падения — при необходимости.

**Ограничения БД:**

- FK на реально существующие таблицы, **ON DELETE согласно действующей политике** (избегать неожиданного CASCADE, если нужен аудит);
- уникальный составной ключ на `tenant_id + endpoint versions + relation_type + direction + semantic detector identity`, с учётом nullable и симметрии; миграция не должна ломаться на `NULL` и повторных версиях;
- транзакционные UPSERT, идемпотентность повторной задачи, опциональный optimistic lock для ревью;
- индексы `(tenant_id, source_document_id, relation_type, review_state)` и аналогичный target; составные индексы выбирать по EXPLAIN/реальным запросам;
- отдельные индексы по `source_version_id`, `target_version_id`, `edge_id` в evidence, `state`/`created_at` у job;
- проверка endpoint в пределах разрешённого tenant/scope при **каждой** записи; нельзя полагаться только на клиентскую проверку;
- для ACL сложнее tenant: доступ к **обоим** документам должен подтверждаться сервисом разрешений на чтение; FK сами по себе этого не обеспечивают;
- только опубликованные актуальные версии в default view, если не задан режим истории;
- миграция Alembic должна иметь валидный downgrade либо документированное восстановление из backup при необратимом изменении;
- обновление данных не должно оставлять «висящих» рёбер после удаления/замены активной версии.

Если PostgreSQL уже поддерживает RLS — сохранять и расширять политику корректно. Не предполагать, что `tenant_id` автоматически закрывает все access groups. Право **редактировать связь** отдельно от права **видеть документы**.

# 5. АЛГОРИТМЫ ПОСТРОЕНИЯ СВЯЗЕЙ

Реализуй **расширяемый интерфейс детекторов** вместо монолита:

```text
RelationDetector.detect(document_version, context) -> list[RelationCandidate]
  ├─ ExplicitReferenceDetector  # реквизиты, цитаты, идентификаторы
  ├─ SemanticSimilarityDetector # reuse existing embeddings / Qdrant
  ├─ VersionRelationDetector    # deterministic version lineage
  ├─ SharedEntityDetector       # phase P2, disabled by default
  └─ LLMRelationDetector        # phase P2, OFF by default
```

Каждый детектор имеет свой `detector_id`, конфигурацию, `algorithm_version`, `is_enabled`, измеряемый budget, отдельное unit-тестирование и `dry_run`. **Пайплайн анализа работает асинхронно через существующую очередь**, не блокирует HTTP-запрос пользователя и не изменяет существующие embeddings/индексы без явной необходимости.

## 5.1. Семантическая близость — безопасный MVP

1. Используй **уже рассчитанные** embedding-векторы из текущего index и текущую модель; определяй её размерность и версию динамически. Нельзя объединять косинусные оценки от разных моделей/размерностей/версий без явной калибровки.
2. Для каждого документа выбирай заранее ограниченное число репрезентативных чанков (заголовки, содержание, разделы, содержательные фрагменты) **или** используй уже существующий качественный document embedding. Выбор обоснуй; документ из сотен чанков не должен создавать сотни тысяч кандидатных пар.
3. Ищи `top_k` **потенциальных соседей** с помощью Qdrant ANN/существующего retrieval-адаптера, **с серверным фильтром tenant/collection/ACL и active published version**. `top_k` — отдельная настройка (разумный пилот, например 10–20 документов на исходный, только после реального теста). Из результатов **исключать сам документ и его повторы**, недоступные документы, удалённые и неопубликованные версии.
4. Агрегируй chunk-level совпадения до связи `document ↔ document` по документированному методу: например max из нескольких независимых подтверждённых пар с ограничением влияния повторяющегося boilerplate; сохранить реальные `chunk-pair` evidence. Не выдавать «один случайно похожий абзац» за высокую связь всего документа.
5. Для порога сходства предусмотреть configurable `min_score`, но **не объявлять начальное число универсальным**. Оценить вручную на русскоязычной и смешанной выборке: 20–30 положительных и 20–30 отрицательных пар (если есть достаточно корпуса); записать найденные precision/recall/false positives. UI-ползунок должен иметь пояснение, что это *сходство*, а не вероятность правдивости.
6. Обеспечь устойчивую генерацию ключей и канонизацию симметричных пар: повторный анализ одних и тех же версий не увеличивает число рёбер/доказательств.
7. Ограничить количество документов-кандидатов, количество фрагментов, объём памяти, Qdrant RPC timeout и число одновременно работающих задач. На текущем ПК семантический граф **не должен запускать массовое новое вычисление embeddings на RTX**, конкурируя с ответами.
8. Если Qdrant недоступен или отсутствуют embeddings — не падать всем графом; показать документы и имеющиеся детерминированные связи, поставить `DEGRADED_NO_VECTOR_SEARCH`; периодически/по ручному действию повторить только соответствующие задачи.
9. Учитывать многодоменность: для разных языков/жанров/длинных документов метрики неодинаковы. Вводить suppression для общих шаблонов (стандартные формы, титульные листы, оглавления), дубликатов и near-duplicate.
10. Не путать **dedup** файлов по SHA256 и **semantic similarity**: это разные признаки. Хеш одинакового содержимого может объединять версии лишь с учётом tenant/ACL/происхождения.

## 5.2. Явные ссылки и цитирования

Сначала внедри низкорисковый детерминированный детектор:

- искать **структурные реквизиты и упоминания** документов в уже извлечённом тексте: точные UUID/внутренние ссылки (если есть), полный заголовок при достаточной уникальности, официальные номера/даты/авторов (с проверкой), DOI/URL как текстовые реквизиты — **без переходов по URL и скачивания**;
- поддержать русские склонения/пробелы/кавычки в разумных рамках; регэкспы нормализуют пробелы, Unicode, Unicode dash, номер `№`, регистр, даты, но не разрушают исходный текст;
- **не связывать по одному распространённому слову**, фамилии без контекста или расплывчатому совпадению названия;
- различать `упомянут` и `ссылается`: если текст не несёт явно ссылочной роли, предложить тип `MENTIONS_DOCUMENT` только после добавления в schema, либо сохранить как candidate с нейтральной подписью; **не подменять определение** `EXPLICIT_REFERENCE`;
- при неоднозначной ссылке кандидаты уходят на подтверждение эксперта, не публиковать ложную направленную связь;
- сохранять **реальный** source chunk и span/section, точную target-version только при достоверной привязке;
- защищаться от regex catastrophic backtracking, мусорных OCR-символов, некорректной кодировки, огромных строк;
- для нормативных актов отличать номер, редакцию и дату; редакция может указывать на другую историческую версию документа.

Подходящий путь: нормализованные метаданные/FTS для генерации кандидатов → строгая проверка по нескольким признакам → создание evidence. Не строить полную декартову матрицу текстов.

## 5.3. Извлечение сущностей и тем — P2

- Ввести сущности с нормализованными идентификаторами, типами (`PERSON`, `ORGANIZATION`, `LAW`, `PRODUCT`, `TERM`, `PLACE`, ... **без обязательного утверждения истинности**), локальными namespace/tenant, алиасами и доказательствами в конкретных фрагментах.
- Важные случаи: омонимия, однофамильцы, похожие названия организаций, акронимы, переименования, множественные языки, привязка к контексту. **Нельзя объединять только по строковому совпадению**.
- Сущности/темы вводить только при необходимости после оценки качества. В MVP не требуется даже одна отдельная таблица сущностей.
- Если сущности между документами приводят к связи `SHARES_ENTITY`, доказательство должно содержать идентификаторы **одной и той же нормализованной сущности** и исходные места упоминаний.

## 5.4. LLM-выводы: дополнения и потенциальные противоречия — P2, по умолчанию OFF

**Опасный этап, строго отделённый от MVP.** Сначала отбирай узкий список кандидатов по explicit relations, общим сущностям, ANN и FTS. Локальная Ollama-модель должна получать только **разрешённые этой задаче** фрагменты из **доступных версий**, а не все файлы.

Условия запуска:

- одна тяжёлая LLM-операция одновременно с соблюдением общей очереди LLM платформы; новые graph jobs — низкий приоритет относительно живого чата;
- токеновый budget, timeout, отказ/повтор с backoff, ограничение VRAM и памяти; не загружать вторую копию модели;
- промпт не должен исполнять инструкции из сравниваемых документов: маркировать их как **source data**;
- вывод **строгий JSON по Pydantic-схеме**: `relation_type`, `source_version_id`, `target_version_id`, `source_chunk_ids`, `target_chunk_ids`, `brief_explanation`, `support_quotes` (если реально в исходных данных), `uncertainty`, `needs_review`;
- результат валидировать **кодом**: IDs из allowlist запроса, chunk belongs to version, цитата существует в исходном фрагменте (нормализованный безопасный поиск), допустимый тип связи, нет пустого основания;
- если схема неверна, чанков нет, цитата не подтверждается, утверждение спорно, контекст недостаточен — `REJECT_INVALID`/`NEEDS_REVIEW`, **не создавать автоматом утверждённое ребро**;
- для противоречий различать реальные несовместимые утверждения и изменения во времени, разные определения, разные уровни детализации, противоположные мнения, разные единицы измерения, разных субъектов;
- в UI писать только «возможное противоречие (требует проверки)», а не «документы противоречат»;
- хранить `model_digest`, prompt hash, seed/параметры если применимы, время анализа, ревизию источников, reviewer outcome; **не обещать детерминизм текста LLM**.

Никаких внешних запросов к hosted LLM. Если локальная модель отсутствует/выключена — интерфейс и основные связи должны работать.

## 5.5. Инкрементальность, версия, удаление и восстановление

Подписаться на **существующие доменные события** (через outbox/очередь/сервис):

- `document_published` → после подтверждения успешной полной индексации запланировать анализ новых опубликованных версий;
- `document_updated/active_version_changed` → связи старой версии перевести в `STALE`, но не терять их аудит; построить и **атомарно сделать видимыми** новые связи после проверок;
- `document_deleted/hidden` → немедленно скрыть узел и все связанные рёбра из всех API при любом статусе фоновой очистки;
- `permissions_changed` → **немедленно** применять новую проверку ACL к выдаче графа и доказательств, **не ждать** пересчёта;
- `document_restored` → восстановить видимость только допустимых ранее связей по активной версии с их ревалидацией; не восстанавливать отвергнутые гипотезы;
- `embedding_model_changed` → пометить сопоставления с прошлой моделью устаревшими, не сравнивать несовместимые оценки;
- `source_chunk_replaced` → ревалидация или снятие evidence.

Если источники живут в одной SQL-БД, использовать транзакционный outbox либо существующий надёжный механизм. Событие нельзя потерять между коммитом документа и отправкой в очередь; повторные события должны быть **идемпотентны**. Workers работают с lease/heartbeat/retry/timeout, `at-least-once` доставкой; корректность достигается повторяемыми UPSERT и статусами, а не надеждой на exactly-once. Сообщения очереди не являются источником истины.

**Сложные случаи:** удаление документа во время анализа; отзыв ACL во время выдачи; смена версии посреди LLM-анализа; двухкратный одновременный запуск на ту же версию; сбой базы между записью evidence и edge; связь после перезапуска контейнера; пустой корпус; orphan endpoints. Все обработать явными тестами.

## 5.6. Очереди и административное управление

Нужны задачи `rebuild_doc_graph`, `analyze_new_version`, `revalidate_links`, `rebuild_collection_graph` (последняя только управляемая batch). Не допускать запуска полного rebuild по одной кнопке без понимания объёма; предложить `dry_run` с оценкой документов/чанков/диска и требуемых операций.

- Состояния: `QUEUED`, `RUNNING`, `PARTIAL`, `SUCCEEDED`, `FAILED`, `CANCELLED`, `RETRYING` + структурированный код ошибки.
- `progress`: processed/total + current stage, а не фиктивный 100%; если total неизвестен — indeterminate.
- Отдельная очередь и rate limit, backpressure; fail-safe pause/resume/cancel; на startup — восстановление зависших `RUNNING`.
- Ретраи только на транзиентных сбоях: timeout Qdrant/DB lock, рестарт worker, временная недоступность сервиса. Фатальные ошибки схемы/ACL/несовместимость embeddings — явный FAILED, без бесконечных повторов.
- Админ видит последние ошибки и может перезапустить **одну** задачу; обычный viewer — нет.

Все маршруты ниже — проектная спецификация. **Сохраняй существующий `/api` prefix, версионирование, auth dependencies, единый формат ошибок и OpenAPI-принципы**. Если в проекте `/api/v1`, согласуй маршруты с ним и отрази реальный URL в документации.

| Метод | Относительный путь | Назначение | Особенности |
|---|---|---|---|
| GET | `/api/graph/overview` | Статистика по видимым документам, тематическим группам и графу | Считать **после ACL**, не выдавать скрытые total |

## 6.2. Мутации с RBAC/ACL и audit

| Метод | Путь | Назначение | Разрешения |
|---|---|---|---|
| POST | `/api/graph/jobs` | Запуск контролируемого анализа по документу/коллекции | admin либо выделенное разрешение |
| POST | `/api/graph/jobs/{job_id}/cancel` | Отмена | owner/admin по политике |
| POST | `/api/graph/edges/{edge_id}/review` | APPROVE/REJECT/REQUEST_CHANGES | reviewer, проверка ACL и версии |
| POST | `/api/graph/edges/manual` | Создание ручной связи с причиной | reviewer/editor с отдельным permission |

Обязательно **reuse действующих ролей и permission модели**, не вводить самостоятельную таблицу «паролей графа». Если соответствующей роли ещё нет, добавлять минимальное новое permission в текущую модель; UI-признаки не заменяют серверную проверку.

## 6.3. Параметры и защита от раздувания ответов

- `depth`: `1..3`, server-side clamp/reject при превышении; `max_nodes` по умолчанию 150–300, конфигурируемый абсолютный предел для данного хоста; `max_edges` аналогично.
- `relation_types[]`: allowlist enum; `min_score`: bounded numeric; `review_states[]`: только те, которые роль вправе читать.
- `collection_ids[]`, `search`, `as_of_version`, `show_archived`, `group_by` — проверка по полномочиям; не принимать неограниченные списки IDs.
- `cursor` — непрозрачный серверно подписанный или проверяемый маркер с фильтрами/контекстом доступа; использовать keyset pagination вместо глубокого OFFSET.
- `truncated: true`, `has_more`, `next_cursor`, `applied_limits`: UI обязан явно показать, что граф **частичный**. Нельзя писать «все документы», когда backend вернул первые 300.
- Query timeout, предельный SQL cost, запрет рекурсивного обхода без depth/cap/cycle protection. Для local traversal с PostgreSQL recursive CTE требуется tenant + ACL на **каждом** уровне, либо ограниченный на сервере BFS с ACL.
- В ответах типов/полей не должно быть случайных `dict` с внутренними ORM-полями: сериализация через Pydantic response DTO и allowlist.

## 6.4. Пример ответа локального графа

Это **схема примера**, а не тестовые данные для продуктивной БД:

```json
{
  "schema_version": "1.0",
  "center_document_id": "d-001",
  "nodes": [
    {"id":"doc:d-001","document_id":"d-001","type":"DOCUMENT","label":"Документ A","status":"PUBLISHED"},
    {"id":"doc:d-002","document_id":"d-002","type":"DOCUMENT","label":"Документ B","status":"PUBLISHED"}
  ],
  "edges": [
    {
      "id":"edge:e-001",
      "source":"doc:d-001",
      "target":"doc:d-002",
      "relation_type":"SEMANTIC_SIMILAR",
      "directed":false,
      "origin":"VECTOR",
      "review_state":"PROPOSED",
      "score":0.82,
      "score_method":"cosine_similarity",
      "evidence_count":2
    }
  ],
  "limits":{"requested_depth":1,"max_nodes":200,"max_edges":400},
  "truncated":false,
  "has_more":false,
  "next_cursor":null
}
```

Не передавай `evidence.text` в данном API. При клике на ребро по отдельному маршруту загружай подтверждающие фрагменты с полной проверкой прав. Число `0.82` в примере **иллюстративно** и не задаёт рекомендуемый порог или вероятность правильности.

## 6.5. Коды ошибок / стабильность API

Единый безопасный формат ошибок, совместимый с текущим backend:

```json
{
  "code": "GRAPH_SOURCE_VERSION_STALE",
  "message": "Связь устарела после обновления документа",
  "request_id": "<id>",
  "retryable": false
}
```

Нужные коды: `GRAPH_NODE_NOT_FOUND_OR_FORBIDDEN` (одинаковый ответ для невидимого и отсутствующего объекта при необходимости), `GRAPH_EDGE_NOT_FOUND_OR_FORBIDDEN`, `GRAPH_VALIDATION_ERROR`, `GRAPH_LIMIT_EXCEEDED`, `GRAPH_BUILD_RUNNING`, `GRAPH_VECTOR_STORE_UNAVAILABLE`, `GRAPH_MODEL_INCOMPATIBLE`, `GRAPH_SOURCE_VERSION_STALE`, `GRAPH_REVIEW_CONFLICT`, `GRAPH_SERVICE_NOT_READY`, `GRAPH_RATE_LIMITED`. Не раскрывать в теле traceback, SQL, token, внутренние физические пути, чужие document IDs.

## 6.6. Кэширование

Кэшировать только тогда, когда ключ содержит **tenant + actor или эквивалентный permission fingerprint + доступные collection scopes + фильтры + ревизию ACL + версию графа**. Безопаснее в MVP не кэшировать детальные ACL-специфичные ответы межпользовательски. Удаление/отзыв ACL должно немедленно инвалидировать выдачу. HTTP ETag, если используется, зависит от видимости; headers `Cache-Control` не должны допускать приватный shared cache.

# 7. WEB UI: ПОЛНОЦЕННАЯ ВКЛАДКА В ДЕЙСТВУЮЩЕМ ПРИЛОЖЕНИИ

1. В существующую навигацию добавь «**Граф связей**» с иконкой network; маршрут `/graph` (или согласованный с проектом). Использовать текущую авторизацию, состояние приложения, toolbar, breadcrumbs, светлую/тёмную тему, компоненты уведомлений и локальный API client.

## 7.3. Функции управления графом

- переключатели `Вся база / Локальный граф / Выбранная коллекция`, выбор центра;
- поиск документа по названию/метаданным, быстрый переход к узлу; не грузить все names для autocomplete;
- глубина локального обхода 1, 2, 3 (по умолчанию 1), кнопка «Показать соседей» с подгрузкой следующего слоя;
- панорамирование мышью, колесо для zoom, кнопки `+`, `−`, `По размеру`, `К центру`, `Сбросить фильтры`, опциональный `Зафиксировать позиции`;
- типы раскладок: `concentric`/`breadthfirst` для локального, `cose` либо fCoSE для общего; для больших выборок применять упрощённую и/или серверную группировку;
- типы узлов отличать **не только цветом**: пиктограмма/форма/легенда; цветовые схемы доступны для дальтонизма;
- типы рёбер: цвет, пунктир, маркер направления; сила/ширина связи — только если это не вводит в заблуждение; отдельное обозначение `POTENTIAL_CONTRADICTION` как гипотезы;
- переключаемые подписи, hover tooltip без плотной накладки, приоритет selected/center, высокоплотные графы без тысячи перекрывающихся надписей;
- длинные имена в подробностях, графическое сокращение labels без потери данных;
- фильтры: коллекция/тип файла/тема/время/тип связи/статус проверки/сходство, счетчики **только видимых после ACL** элементов;
- сохранять в URL неконфиденциальные параметры `doc`, `depth`, `types`, `layout` для sharing **в рамках авторизованного продукта**; нельзя кодировать токены или скрытый контент;
- кнопка таблицы «Связанные документы», потому что граф не всегда лучший формат для чтения и accessibility;
- экспорт `PNG/SVG` текущей видимой сцены без скрытых элементов и JSON/CSV только через server-side ACL экспорт; обезличивать/не экспортировать лишние внутренние поля. Учесть размер файла, browser memory, запрет неавторизованного bulk export;
- состояния `нет документов`, `нет связей`, `модель сходства ещё не настроена`, `идёт анализ`, `частичный граф`, `временная недоступность`, `доступ ограничен`, `ошибка API` с правильными действиями.

## 7.4. Подробная панель связи

По нажатию на ребро выводи:

- документ A и B: заголовок, версии, даты, ссылки на просмотрщик;
- тип, направление, источник (`вычислено по embedding`, `явная ссылка`, `предложено LLM`, `вручную`);
- для векторной связи: `score_method`, score, версия модели, **«похожесть не доказывает истинность»**;
- для явной ссылки: найденное место ссылки (страница, раздел, фрагмент);
- для LLM: краткое объяснение, исходные подтверждающие фрагменты, видимый `не подтверждено`;
- время построения/проверки, кем принято решение, статус версии, `STALE` причина;
- ссылки «Показать сравнение двух фрагментов», «Открыть документ», «Показать только эти узлы»;
- экспертные кнопки (только с серверным permission): `Подтвердить`, `Отклонить`, `Исправить тип`, `Указать причину` — confirmation dialog, optimistic version check, обработка 409 Conflict.

Фрагменты должны быть экранированы, ограничены разумной длиной и подгружаться **после** проверки прав. Поиск в копии документа — только в рамках разрешённого просмотра.

## 7.5. UX, доступность и состояние

- React + TypeScript, типизированные DTO, hooks, единый API client и error handling;
- отдельный контролируемый GraphRenderer с `useEffect` init/cleanup, `ResizeObserver` если он есть в среде, `cy.resize()` при изменении контейнера; не вызывать часто тяжелую автоматическую раскладку;
- loading skeleton, debounced search, AbortController для смены фильтра/перехода/размонтирования, отмена старых ответов, защита от race conditions;
- при выборе нового центра не должно мигать старое содержимое под новыми заголовками;
- keyboard navigation через альтернативный список/таблицу и фокусируемые controls, tooltips не единственный канал информации;
- контрастность и focus-visible, читабельные русские надписи, работа при масштабировании браузера 125–200%; адаптивность от ~1280 px до мобильного;
- UI не должен обещать полное покрытие, если загружена только часть графа — всегда показывать `N узлов / M связей показано; есть ещё`;
- не отображать score «в процентах вероятности», если его нельзя калибровать;
- сохранять пользовательские предпочтения фильтров безопасно (например local state/URL или серверные user settings); в `localStorage` не хранить чувствительные документы/токены.

# 8. БЕЗОПАСНОСТЬ: ОБЯЗАТЕЛЬНАЯ МАТРИЦА РИСКОВ

**Риск №1 — граф раскрывает существование скрытых документов даже без текста.** Поэтому нет «безопасного публичного графа» без полного контроля видимости.

## 8.1. Проверки доступа на сервере

1. Пользователь может видеть узел лишь если имеет действующее разрешение на соответствующий документ/активную версию.
2. Ребро видно, только если пользователь вправе читать **обе** его конечные точки **и данный тип связи**. В ответе не должно быть «обрезанной» линии с названием скрытого документа.
3. Evidence — отдельная проверка доступа к обоим source documents и версиям/чанкам. При отзыве прав на один конец скрыть и ребро, и даже его count.
4. Агрегации, темы, топ-связанные документы, count, autocomplete, экспорт, статусы и даже ошибки должны рассчитываться **после фильтрации доступа**. Не выдавать глобальные количества через сортировку, timings или total.
5. Изоляция `tenant` **и** `access_groups/owner` проверяется не только в API, но и в SQL/Qdrant/adapters. Один tenant не означает общую видимость документов.
6. По умолчанию отношение между документами разных tenants **запрещено**, включая поиск candidates. Если когда-либо потребуется shared knowledge, это отдельный строгий проект с разрешениями и аудитом.
7. Роль `viewer` не создаёт связи и не запускает дорогостоящий rebuild; `reviewer` принимает решения только для доступных документов; `admin` не обязательно автоматически является владельцем всех конфиденциальных документов, действовать по текущей политике.
8. Определить поведение 401/403/404 так, чтобы не существовал enumeration endpoint для закрытых document IDs/edge IDs.
9. Массовый экспорт запрещён или строго rate limited и permission gated; всегда исключать скрытые/черновые версии.

## 8.2. Входные данные и web безопасность

- Pydantic DTO: лимиты длин текстов, enum allowlist, numeric bounds, ограничение числа IDs, одинаковая server-side валидация для всех маршрутов.
- SQLAlchemy параметризованные запросы, проверенные имена колонок/полей сортировки, никаких raw SQL от LLM.
- Не использовать `dangerouslySetInnerHTML` с загруженным текстом/LLM; React по умолчанию экранирует текст, а кастомные Cytoscape tooltips тоже должны вставлять его как **textContent**, не как HTML.
- Не применять eval/Function/new Function к данным; URL внутри документов не подгружать автоматически, `javascript:`/`data:` ссылки не исполнять.
- Унаследовать сессионную auth/CSRF защиту; CORS не расширять до `*` при cookies, ограничить origin; secure cookies/TLS по режиму deployment.
- CSP: максимально запретить внешние источники, разрешить только необходимые локальные script/style/worker/connect источники с учётом build; `connect-src 'self'` и конкретные локальные endpoints, никаких произвольных доменов. Проверить реальные требования libs, а не сломать основной UI.
- Хранить аудит действий экспертов; запрещено редактировать/стирать audit event пользователю без соответствующей политики.
- Логи: request_id, job_id, hash IDs, duration, code; **не логировать полные документы, выделенные фрагменты, секреты, access tokens, приватные embedding vectors**.
- Docker/WSL: не открывать PostgreSQL/Qdrant/Valkey/Ollama наружу; использовать текущую внутреннюю сеть контейнеров. Публикация web/API — по текущей безопасной конфигурации (localhost либо авторизованный reverse proxy).
- Ограничить ресурсоёмкие обходы графа, частоту экспорта и графовые rebuild операции. Нельзя позволять одному viewer вызвать сотни тысяч Qdrant запросов через UI.
- Privacy: не сохранять конфиденциальные заголовки/сниппеты в глобальном браузерном кэше/service worker или `localStorage`.

# 9. ПОЛНОСТЬЮ АВТОНОМНАЯ РАБОТА (OFFLINE-FIRST)

**Целевой режим:** все зависимости, модели, контейнеры и фронтенд уже подготовлены; пользователь отключает внешнюю сеть и продолжает работать с RAG и новым графом по локальному адресу. Внутренняя сеть WSL2/контейнеров **остаётся доступной**.

## 9.1. Сборка и поставка

- `npm ci` с lockfile в **подготовительном** online-окружении; production `dist/` содержит все нужные JS/CSS/assets/icons/fonts. Никакой автозагрузки CDN в runtime.
- Зафиксировать совместимые версии в package lock и Python lock; не ставить `latest`/floating dependencies во время offline запуска.
- Для восстановления без интернета сформировать набор или инструкции: локальный npm-cache/пакеты (если нужна офлайн-пересборка), Python wheelhouse (если нужен офлайн-rebuild), `docker save`/`docker load` или локальный registry по модели проекта; model weights/токенизаторы/OCR-ресурсы полностью локальны.
- **Не требовать пересборки React-приложения при каждом offline-запуске**: обслуживать собранные статические ресурсы через уже существующий reverse proxy.
- Frontend не использует Google Fonts, внешние изображения, внешнюю favicon/иконки, maps/CDN, telemetry и error trackers. Все необходимые шрифты — системные или локально поставляемые с проверенной лицензией.
- Никаких обязательных license check, npm install, pip install, Ollama pull, ModelScope/Hugging Face fetch в рабочем режиме.
- Для новых пакетов проверить их transitives и `postinstall` скрипты до установки. Если в offline-сборке toolchain требует fetch — кэшировать в подготовительном режиме и отключить дальнейшие запросы.

## 9.2. Реальное тестирование без интернета

1. В режиме подготовки установить зависимости, собрать production assets, подготовить service images и модели.
2. Отключить/заблокировать внешний маршрут к интернету, **сохранив локальную docker/WSL сеть**.
3. Очистить browser cache или использовать свежий профиль, открыть `/graph` — должен загрузиться без единого external HTTP(S)/DNS запроса и без remote assets.
4. Авторизоваться через локальную систему, открыть global/local граф, фильтры, evidence, выполнить небольшой rebuild и локальный LLM анализ, если он включён.
5. Зафиксировать в `docs/graph/OFFLINE_TEST_REPORT.md`: дату, метод блокировки, скрин/экспорт Network HAR **с удалёнными секретами**, список запросов к разрешённым локальным адресам, результаты, исключения. Проверить startup после перезагрузки хоста.
6. Не путать «нет интернета» и «нет docker DNS»; если выключена внутренняя сеть, сервисы могут не найти друг друга — это не дефект web модуля, но инструкцию по безопасной изоляции написать.

## 9.3. Размещение данных на дисках

Известные условия: 32 ГБ RAM и небольшой остаток SSD, основной HDD около 2 ТБ. До изменений **обнаружь настоящие пути размещения PostgreSQL/Qdrant/WSL virtual disk/volumes, backups и caches**. Не создавай новый большой store под Windows `C:`. Рекомендации:

- хранить граф в текущей PostgreSQL — не вводить второй набор больших документальных embeddings;
- evidence обычно **ссылаться на существующие chunks**, вместо копирования полного текста в новые таблицы;
- временные export/layout cache очищать по TTL, ставить квоты;
- не выполнять массовый `REINDEX`, `VACUUM FULL`, перегенерацию embeddings или перенос WSL VHDX без явного плана и резервного копирования;
- учесть низкую IOPS HDD и избегать огромных случайных запросов; индексы и batch operations измерять на реальном железе;
- резервная копия на тот же HDD **не считается независимой** от отказа носителя.

# 10. ПРОИЗВОДИТЕЛЬНОСТЬ, ЛИМИТЫ, НАБЛЮДАЕМОСТЬ

## 10.1. Управляемые лимиты, а не догадки

Ввести конфигурацию `GRAPH_*` через существующий config system; реальные значения подобрать на замерах. Разумные **стартовые ориентиры для проверки**, а не универсальные ограничения:

```dotenv
# Это пример параметров для .env.example; не вносить без проверки текущего config.
GRAPH_ENABLED=true
GRAPH_LLM_ANALYSIS_ENABLED=false
GRAPH_DEFAULT_DEPTH=1
GRAPH_MAX_DEPTH=3
GRAPH_DEFAULT_NODES=200
GRAPH_HARD_MAX_NODES=500
GRAPH_DEFAULT_EDGES=400
GRAPH_HARD_MAX_EDGES=1500
GRAPH_NEIGHBOR_TOP_K=12
GRAPH_SEMANTIC_MIN_SCORE=0.0  # placeholder: до калибровки не показывать как «качество», назначить реальный порог по тестам
GRAPH_BUILD_CONCURRENCY=1
GRAPH_READ_TIMEOUT_SECONDS=15
GRAPH_JOB_TIMEOUT_SECONDS=600
GRAPH_EXPORT_ENABLED=false
GRAPH_LAYOUT_FCOSE_ENABLED=false
```

**Не оставляй «0.0» как рабочий порог семантических связей без калибровки.** На реальном корпусе зафиксируй обоснованный консервативный стартовый порог либо временно отключи `SEMANTIC_SIMILAR`, показав пользователю запрос на калибровку/тесты. Правила порога должны применяться к **известному score_method**, не к разнотипным модельным баллам.

Администратор может безопасно менять пороги и лимиты в конфиге/панели; настройки должны валидироваться, обновляться с записью в журнал и не давать одному клиенту обойти hard limits.

## 10.2. Контроль производительности

- Не рендерить весь граф коллекции за один fetch. Глобальный граф запускается с агрегатами/кластеризацией и подгрузкой по scope; при необходимости показывать самый связный/репрезентативный срез с честной меткой «частичная выборка».
- Browser workers для тяжёлой компоновки/analytics — только если действительно нужны и доступны офлайн, без внешних imports; избегать layout loop при каждом обновлении React state.
- Для 500 элементов на графе измерить время рендера и отклик UI; затем проверить 1 000+ элементов как нагрузочный эксперимент, **без обещания фиксированного FPS**.
- Сервер: bounded queries, индексирование по проверенным планам, `EXPLAIN ANALYZE` на тестовых/обезличенных данных, keyset pagination, batch fetch, запросы без N+1.
- Скорость Qdrant зависит от типа индекса, payload filtering, HDD/CPU, размерности и размера корпуса; measure before optimization.
- Не хранить все чанки корпуса в памяти и не пересчитывать embedding через браузер; графическое рисование — задача browser CPU/GPU, не LLM GPU.
- Если FPS падает, деградировать gracefully: скрыть labels, анимации, уменьшить выборку, предложить локальный режим; при необходимости подготовить интерфейс замены renderer на Sigma.js.

**Целевые метрики для пилота:**

- страница открывается на подготовленном корпусе 100–500 документов без явных ошибок JS/API;
- 95-й перцентиль запросов neighborhood в обычном масштабе по возможности ≤ 2 с на тестовом стенде (цель, не гарантия); фактическое p50/p95 измерить;
- смена фильтра без зависания браузера и без full-page reload;
- загрузка графа не запускает незапланированную генерацию LLM;
- после отката к предыдущему маршруту RAG чат и загрузка документов работают как до добавления графа.

Если измерения не соответствуют целям, **отрази результаты и bottlenecks**, предложи конкретную оптимизацию, не подменяй цифры оценками.

## 10.3. Метрики/логи

Соблюдать текущие conventions OpenTelemetry/Prometheus/structlog, если они есть; **не внедрять тяжёлый мониторинговый стек только ради графа**. Минимальные события:

- `graph_request_duration_ms{route, outcome}` (без document title/id в label);
- `graph_nodes_returned`, `graph_edges_returned`, `graph_truncated_total`;
- `graph_build_duration`, `graph_build_job_total{state}`, `graph_candidates_total{detector,type}`, `graph_reviews_total{decision}`;
- `graph_index_lag`, `graph_stale_edges_count`, `graph_evidence_missing_count`;
- предупреждения `GRAPH_ACL_DENY`, `GRAPH_VECTOR_UNAVAILABLE`, `GRAPH_SCHEMA_INCOMPATIBLE`, `GRAPH_EXTERNAL_REQUEST_ATTEMPT` (если применим).

Логировать trace_id/request_id, обезличивать ID. Роль администратора имеет безопасную страницу диагностики, скрытую для обычных пользователей.

# 12. ТЕСТЫ: ЧТО ДОЛЖНО РАБОТАТЬ НА РЕАЛЬНОМ ПРОЕКТЕ

## 12.1. Unit tests (Python/TS)

- парсинг ссылок: кириллица, номера, даты, Unicode, недоверенный HTML, OCR-мусор, неоднозначные title;
- нормализация симметричных endpoint IDs, сохранение directed edge, уникальность;
- вычисление агрегированного score и отказ при несовместимом embedding model;
- отделение `review_state` от `score`, запрет auto-approval LLM гипотез;
- Pydantic input/output bounds, DTO excludes private fields;
- верные статусы `STALE`/`RETRACTED` при событиях;
- null evidence, невалидная ссылка на chunk, missing data, corrupt UTF-8;
- UI typeguards, safe text rendering, фильтры, графические адаптеры.

## 12.2. Integration tests (на тестовой БД и тестовом Qdrant)

- новый документ опубликован → job → graph edge + actual evidence → доступен в API;
- rebuild same version дважды → **число идентичных рёбер/доказательств не растёт**;
- изменили документ → старые связи скрыты/помечены stale, новые привязаны к правильной версии;
- удаление/скрытие/восстановление/изменение ACL мгновенно влияет на выдачу;
- tenant A и tenant B с одинаковыми названиями документа → **нет cross-tenant edge или подсказки**;
- пользователь с доступом только к A и не к B → не видит ни A—B edge, ни B title, ни B-evidence/count;
- ACL на уровне access_group внутри одного tenant проверяется отдельно;
- отказ Qdrant, restart worker, timeout DB, stale lease, outbox replay, одновременные задачи;
- review approve/reject/stale optimistic concurrency и полный audit;
- paginated global view и local depth cap, циклы, duplicate edges, huge corpus bounds;
- экспорт JSON/CSV соблюдает ACL; вредоносная строка не приводит к XSS/CSV formula injection (экранировать опасные leading `=`, `+`, `-`, `@` при экспорте в табличные форматы).

**Важно:** не запускать destructively against production dataset. Для тестов отдельная БД/tenant и фикстуры; очистка тестовых данных управляемая. Не копировать реальные конфиденциальные тексты в репозиторий, отчёты или скриншоты.

## 12.3. UI E2E (Playwright или уже применяемый инструмент)

- перейти в существующий web app → авторизация → вкладка «Граф связей» → реальные API;
- глобальный граф: toolbar, загрузка, легенда, панорамирование, fit, фильтры, truncated banner;
- локальный граф 1/2/3 шага и подгрузка соседей; переход в исходный документ;
- панель edge → evidence (2 документа, источники) → безопасное открытие fragment/reader;
- reviewer approval/rejection + forbidden action для viewer;
- fast search/filter toggling не показывает stale result;
- открытие/закрытие страницы несколько раз, проверка отсутствия memory leaks и duplicate listeners;
- светлая/тёмная тема, viewport width, zoom browser 200%, keyboard navigation;
- XSS titles, HTML-like snippets, malicious URLs rendered as plain text;
- браузер без доступа к внешней сети полностью работает с локальным backend.

## 12.4. Нагрузочные тесты и измерения

Подготовить генератор **синтетических не конфиденциальных** графовых тестовых записей на 100, 500, 1 000, 5 000+ узлов и контролируемой степени связности **в отдельной тестовой среде**. Приоритет теста реального пилота 100–500 документов, затем проверка запаса масштабирования. Метрики: latency p50/p95/p99, FPS/interactions, browser memory, Postgres query time, Qdrant calls, RSS CPU, VRAM, HDD I/O, число job retries. # 15. ФОРМАТ ФИНАЛЬНОГО ОТЧЁТА ОТ CURSOR

После завершения работ выведи **на русском языке** отчёт с этими разделами:

1. **Обнаруженный стек и состояние:** фактические компоненты, отклонения от прежних roadmap, найденный адрес/маршрут web графа.
2. **Что реализовано:** список P0/P1/P2 с состоянием `DONE` / `PARTIAL` / `NOT DONE`; без выдуманных галочек.
3. **Изменённые файлы и миграции:** что добавлено/изменено, причина, backcompat.
4. **Демонстрация рабочего сценария:** шаги по кликам в текущем UI: загрузка реальных разрешённых документов → построение → граф → доказательства → переход в читатель документов → обновление/удаление → корректная перестройка.
5. **Безопасность:** результаты по tenant, access_group/owner, revoke, edge/evidence/count, инъекциям, permissions, audit.
6. **Автономность:** запись теста без внешней сети, список локальных ресурсов, что нужно предварительно подготовить.
7. **Производительность:** измерения p50/p95, memory, нагрузка CPU/GPU/HDD на этом ПК; реальные цифры vs цель.
8. **Проверенные команды:** lint, typecheck, pytest, integration, E2E, production build, `docker compose config`, healthcheck, database migration check и фактический вывод PASS/FAIL/SKIP.
9. **Открытые зависимости:** библиотеки, версии, лицензии, репозитории, причины выбора.
10. **Проблемы и пути решения:** блокеры, неточные данные, доступность моделей, что не удалось воспроизвести и почему.
11. **Как запустить и откатить:** точные команды для существующего WSL2/Docker workflow и пошаговая процедура восстановления.
12. **Дальнейшее развитие:** P2 (LLM relation extraction, entity graph, GraphRAG, graph analytics), только после сдачи MVP.

**Финальное правило:** не сообщай «готово», если существует только интерфейс с мок-данными, API не применяет ACL, не проверен offline, реальные связи не сохраняются или после обновления документов граф показывает устаревшие сведения как актуальные. Продолжай реализовывать до выполнения P0 либо ясно покажи конкретный технический блокер с максимально возможной выполненной частью и воспроизводимыми шагами исправления.
